# 2026-11-20 19:00 — `/config app remove`

## Why

Taking an app's service out of the Compose file disables the app but keeps everything Botman created for it. There was no way to delete an app once it was no longer wanted.

## Change

- New `src/botman/app_removal.py` (`AppRemovalService`). `plan` refuses an app whose service is still in the installed Compose file (`AppNotDisabledError`). `remove` recomputes the plan under the stack lock and refuses if it changed (`AppRemovalStaleError`), then removes, stopping at the first failure so it can be retried:
  - the service's containers (by Compose labels) and its built image, trying both `<project>-<service>` and `<project>_<service>`;
  - `apps/APP/` and the env file on the target (the env file is kept when another app in the stack uses it);
  - the Git cache and the default-path deploy keypair on central (a custom key path is kept);
  - the config entry, under the server's agent lock, then an agent sync when live logs were on.
- `/config app remove APP` previews this with Remove/Cancel buttons (`commands/app_remove.py`) and afterwards deletes the app's Discord log webhook, best-effort.
- The Confirm/Cancel view moved to `commands/confirm.py` and is shared with `/config compose apply`. `project_containers` is now a public function in `compose.py`.
- Volumes are never deleted. The agent's per-app checkpoint file on the target is left in place.

## Tests

- Unit (`tests/central/test_app_removal.py`): refusal for an enabled app, removal order and resulting state, keeping config after a failed target step, the stale-preview refusal, kept shared env file and custom key, removal without a Compose file, and plan rendering.
- Integration: a disabled (not yet applied) app's container, built image, release directory, and env file are removed on all three CI providers, and the other app's container is untouched.
