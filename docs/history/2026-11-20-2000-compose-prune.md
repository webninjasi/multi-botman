# 2026-11-20 20:00 — `/config compose prune`

## Why

`/config compose apply` and `/config app remove` never delete volumes or networks. Ones the Compose file no longer declares stayed on the target with no way to remove them through Botman.

## Change

- `ComposeAdminService.plan_prune` / `prune` in `compose.py`. The plan lists networks and volumes labelled with the stack's Compose project whose runtime name is not declared by the installed file. `declared_resource_names` maps declared entries to `<project>_<key>` or their `name:`, and always counts the implicit `default` network. External resources have no project label, so they never match.
- Volumes are listed but kept unless `include_volumes` is set. `prune` recomputes the plan under the stack lock, refuses on a change (`ComposeApplyStaleError`), then runs `network rm` and, when included, `volume rm`. The result fails if either step fails; the runtime keeps anything still in use.
- `/config compose prune [volumes]` previews with Prune/Cancel buttons (`commands/compose_apply.py`).

## Tests

- Unit: only undeclared project resources are listed (custom `name:` and `default` respected), volumes removed only when included, an empty plan when only kept volumes remain, failure reporting, the stale-preview refusal, and plan rendering.
- Integration: a dropped network is removed while a dropped volume is kept by default, the volume is removed with `volumes` on, and a declared volume survives, on all three CI providers.
